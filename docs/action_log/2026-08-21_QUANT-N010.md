## Evidence semantics

A green GitHub workflow proves only:

```text
repository verifier execution
```

It does **not** prove:

```text
external Render runtime truth
```

Therefore every valid receipt must contain:

```text
execution_status       = PASS
 evidence_kind          = REPOSITORY_VERIFIER_EXECUTION
 external_runtime_truth = NOT_PROVEN
 promotion              = DENY
 pass_inheritance       = false
 unknown_is_not_pass    = true
 layer                  = LAYER_1_ROOM_01
```

## One-FSM gate rule

There is one Forensic FSM, not separate Forensic universes:

```text
DB_EXISTENCE
 -> DB_BINDING
 -> SECRET_RESOLUTION
 -> DB_TLS_ADMISSION
 -> NETWORK_ORIGIN_PROOF
 -> DB_ROUND_TRIP
 -> PROMOTION
```

Each gate owns its own evidence. PASS only makes the next gate reachable; it never grants the next gate PASS. FAIL or UNKNOWN stops reachability and later gates are `UNREACHED`, not PASS.

The distinction is:

```text
DB_EXISTS = the room exists
DB_BOUND  = the service has the room's key
ROUND_TRIP = the service actually entered, wrote, read, and verified the evidence
PROMOTION = governance decision
```
